01 — Resumen Ejecutivo

Resumen ejecutivo de la aplicación

🎯

¿Qué es Kairo?

Herramienta web de gestión ágil diseñada para equipos de desarrollo de software. Centraliza la planificación de sprints, el seguimiento de tareas y las métricas de productividad en un solo lugar.

  • Gestión de proyectos, sprints y backlog
  • Vista Kanban y lista con filtros por estado, prioridad y asignado
  • Dashboard con 9 widgets de métricas en tiempo real
  • Historial de actividad inmutable por tarea
⚡

¿Cómo mejora la productividad?

Elimina el tiempo de seguimiento manual que consume cada reunión de sprint. Los managers ven el estado real del equipo en segundos; los developers actualizan su trabajo sin cambiar de contexto.

  • Visibilidad inmediata: velocidad, eficiencia y carga por persona
  • Alertas automáticas de sprints por vencer y tareas bloqueadas
  • Registro de horas reales al completar → datos objetivos por sprint
  • Los KPIs del dashboard evidencian la distribución real del trabajo
🤖
✦ Feature de IA

NLU con Claude API — Bot de Telegram

Integramos Claude API (claude-haiku-4-5) en el bot de Telegram de Kairo mediante un componente de procesamiento de lenguaje natural (NaturalLanguageRouter). En lugar de memorizar comandos, los usuarios —especialmente los miembros del equipo— escriben en lenguaje natural: "dame mis tareas", "marca la tarea 5 como done con 2 horas", "pon la tarea 3 en progreso". Claude clasifica la intención, extrae los parámetros y ejecuta el comando. Nuestro equipo lo utilizó recurrentemente durante el proyecto, siendo los miembros no-administradores quienes más lo adoptaron para consultar y actualizar tareas sin abrir el portal web.

OCI Deployment — Kairo · Equipo 33
Containerization
  • Dockerfile multi-stage build (Maven → JRE)
  • Eclipse Temurin 17 JRE en imagen final
  • Sin JDK en runtime (imagen optimizada)
  • Image tagged con SHA de commit OCIR
Cloud Provider Integration (OCI)
  • Oracle Container Engine for Kubernetes (OKE) OCI
  • 3 nodos VM.Standard.E3.Flex (2 OCPU, 6 GB RAM)
  • Oracle Autonomous Database — ATP OCI
  • OCIR — mx-queretaro-1.ocir.io OCI
  • OCI Load Balancer — IP_HASH, port 80→8080
  • Virtual Cloud Network (VCN) — 10.0.0.0/16
  • NAT Gateway + Service Gateway configurados
  • OCI Object Storage — deployment config
  • Oracle Wallet para conexión ADB
  • OCI Vault — gestión de secretos OCI
Security
  • JWT authentication (HMAC-SHA256, 24h expiry)
  • BCrypt password hashing
  • Kubernetes Secrets (dbpassword, wallet, UI)
  • Oracle Wallet montado como volumen en pods
  • Stateless sessions — CSRF disabled
  • CORS configurado
  • Autorización por proyecto (manager / participant)
  • K8s NetworkPolicy — restricción entre pods
  • K8s RBAC — ServiceAccount / RoleBinding
Resilience
  • 2 réplicas en Deployment
  • Topology Spread Constraints (max 1 pod/nodo)
  • HikariCP connection pooling (Spring Boot default)
  • Manual rollback pipeline (GitHub Actions) DevOps
Scalability
  • 3 nodos OKE con capacidad de escalar
  • Database connection pooling (HikariCP)
  • Paginación eficiente (default 20, max 500)
  • Kubernetes rolling update strategy
  • HPA — Horizontal Pod Autoscaler
DevOps & CI/CD
  • GitHub Actions CI — tests en cada PR/push CI
  • Backend unit tests (JUnit 5 + Mockito, 8 suites)
  • Frontend tests (React Testing Library)
  • GitHub Actions CD — build → OCIR → OKE CD
  • Aprobación requerida para deploy a producción
  • Zero-downtime rolling deployment
  • Rollback disponible via workflow_dispatch
API Management
  • RESTful API design (Spring Boot 3)
  • SpringDoc OpenAPI — Swagger UI
  • Spring Security por endpoint
  • Claude API (Haiku 4.5) — NLU bot IA
  • OCI API Gateway
Data Management
  • ADB automated backups OCI
  • Data encryption at rest (ADB)
  • Oracle Wallet — conexión TLS al DB
  • ddl-auto: validate (schema protegido en prod)
Cost Optimization
  • ADB Free Tier habilitado

11 — Lessons Learned

Lessons Learned

⚙️ Tecnología — OCI & DevOps
Lo que funcionó
  • Una vez superado el deploy inicial en OCI, la operación diaria es fluida — pasas la curva y estás del otro lado
  • CD eliminó la fricción de subir cambios — push a master y el pipeline se encarga del resto
  • CI actuó como red de seguridad — los pipelines de pruebas automáticas evitaron que errores importantes llegaran a producción
  • La diferencia entre el antes y el después de CI/CD es notable — velocidad y confianza aumentaron significativamente
Lo que haríamos diferente
  • Implementar DevOps desde el día uno y desarrollar sobre esa base, no como algo que se agrega después
  • No subestimar la curva de aprendizaje de OCI — reservar tiempo dedicado a entender la infraestructura antes de empezar a desarrollar
🤖 Inteligencia Artificial — NaturalLanguageRouter
Lo que funcionó
  • Integrar Claude API con Spring Boot resultó directo una vez definida la arquitectura del componente
  • El system prompt bien diseñado fue la clave — cuando representa fielmente el objetivo del NLU, la clasificación es precisa y confiable
  • Limitar max_tokens a 150 mantuvo las respuestas enfocadas y el costo bajo
Lo que haríamos diferente
  • Dedicar más tiempo al diseño del system prompt desde el inicio — fue el factor más crítico y se subestimó
  • Crear un conjunto de pruebas para el NLU antes de integrar, no después — la clasificación incorrecta inicial tardó en detectarse
  • Documentar las iteraciones del prompt para no repetir configuraciones que no funcionaron
👥 Equipo & Gestión — Kairo gestionado con Kairo
Lo que funcionó
  • Desde que tuvimos la herramienta lista la usamos para gestionar el propio proyecto — fuimos nuestros propios usuarios
  • Los indicadores de story points + horas reales dieron un panorama más preciso que el conteo de tareas solo
  • Un developer con pocas tareas pero muchas horas vs otro con muchas tareas y pocas horas — los KPIs revelaron la carga real y el admin pudo redistribuir sobre la marcha
  • La visibilidad del dashboard facilitó tomar decisiones informadas en cada sprint
Lo que haríamos diferente
  • Empezar a usar la herramienta desde el Sprint 0, no esperar a que esté "lista" — los datos tempranos son igual de valiosos
  • Establecer una convención de story points desde el inicio para que las comparativas entre sprints sean consistentes
